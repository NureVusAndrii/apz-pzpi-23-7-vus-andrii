Доповідь повинна супроводжуватись:

3 ОПИС ВИКОНАНОЇ РОБОТИ

3.1 Вибір патерна проєктування
Було обрано патерн проєктування «Factory method» або «Заводський метод». Цей патерн належить до категорії породжувальних патернів і описаний у відомій книзі банди чотирьох – GoF Design Patterns. Даний патерн використовується в багатьох сучасних фреймворках та бібліотеках, тому розуміння цього патерна є важливим для побудови гнучких та масштабованих програмних систем.

3.2 Що таке патерни проєктування та GoF
Патерни проєктування – це типові перевірені рішення поширених проблем у програмуванні. Вони не є готовим кодом, а радше шаблоном або підходом до організації архітектури програми.
Найвідомішу класифікацію патернів створили автори книги «Design Patterns: Elements of Reusable Object-Oriented Software», яких називають «Gang of Four» (англ. Банда Чотирьох) або скорочено «GoF». До цієї групи входили Еріх Ґамма, Річард Гелм, Ральф Джонсон та Джон Вліссідес.
У книзі описано 23 класичні патерни, які поділяються на три групи: породжувальні, структурні та поведінкові. Структурні шаблони стосуються структури класів, зокрема успадкування та композиції, а поведінкові пропонують рішення для покращення взаємодії між об’єктами. «Заводський метод» належить до породжувальних патернів, тобто таких, що відповідають за створення об’єктів. Його основна мета – це зробити процес створення об’єктів більш гнучким та незалежним від конкретних класів.

3.3 Ознайомлення з патерном «Заводський метод»
«Factory Method» визначає інтерфейс для створення об’єктів, але дозволяє підкласам вирішувати, який саме клас буде створений. Іншими словами, базовий клас описує сам механізм роботи, а конкретна реалізація створення об’єкта переноситься в дочірні класи.
У книзі цей патерн ще називають «Virtual Constructor», тобто віртуальний конструктор. Основна ідея полягає в тому, щоб не створювати об’єкти напряму через оператор «new» у коді клієнта. Замість цього використовується окремий фабричний метод.
Це дозволяє зробити систему менш залежною від конкретних класів і значно полегшує її розширення. Наприклад, якщо потрібно додати новий тип об’єкта, достатньо створити новий підклас фабрики, не змінюючи вже існуючий код.

3.4	Опис проблеми, яку вирішує патерн
Без використання «Factory Method» код часто стає жорстко прив’язаним до конкретних класів. Наприклад, якщо програма напряму створює об’єкти інших класів, то при додаванні нового класу доведеться змінювати вже існуючий код.
Це порушує принцип відкритості-закритості, згідно з яким програмні модулі мають бути відкритими для розширення, але закритими для модифікації. Тобто код повинен бути підготовлений до безболісного додання нового функціоналу.
Можна навести приклад на картинці. У нас є розроблений застосунок для керування логістикою вантажівок, і він користується настільки великою популярністю, що є потреба розширити його для керування логістикою кораблів. Але застосунок складається з одного центру керування логістикою, тому для того, щоб додати кораблі, необхідно маже повністю змінити логіку цього центру. Саме цю проблему і вирішує «Заводський метод».

3.5	Опис рішення, яке пропонує патерн
«Factory Method» пропонує перенести створення об’єктів у спеціальний метод, який може перевизначатися у підкласах. Базовий клас працює лише з абстракціями та викликає заводський метод, не знаючи конкретного типу об’єкта.
Наприклад, для нашої попередньої проблеми ми можемо визначити інтерфейс логістики з методами, котрі необхідні як для кораблів, так і для вантажівок. Тоді кожен із підкласів зможе перевизначати та використовувати методи інтерфейсу для власних потреб, що значно спрощує додання нових видів перевезень і в майбутньому.
Таким чином, логіка створення об’єктів інкапсулюється в одному місці. Код стає більш гнучким, легше підтримується та розширюється. Також це дозволяє будувати фреймворки, які працюють із загальними інтерфейсами, а не з конкретними класами.

3.6	Опис структури патерна
У «Заводському методі» є чотири основні учасники:
-	Продукт. Це загальний інтерфейс або абстрактний клас для всіх створюваних об’єктів.
-	Конкретний продукт. Це конкретна реалізація продукту. Наприклад, корабель чи вантажівка.
-	Творець. Це базовий клас, який оголошує фабричний метод. Також він може містити основну бізнес-логіку, яка працює з продуктами через абстракцію продукту.
-	Конкретний творець. Це підклас, який перевизначає фабричний метод і повертає конкретний продукт.

Головна перевага такої структури полягає в тому, що творець не залежить від конкретних реалізацій продуктів. Він працює лише через інтерфейс продукту, що забезпечує слабке зв’язування між компонентами системи.

3.7	Переваги та недоліки патерна «Заводський метод»
«Factory Method» має кілька важливих переваг. По-перше, він зменшує залежність між класами та дозволяє працювати через абстракції. По-друге, полегшує розширення системи: нові типи продуктів можна додавати без зміни існуючого коду. Також цей патерн добре підтримує принципи об’єктно-орієнтованого програмування.
Проте існують і недоліки. Основний мінус – збільшення кількості класів та складності структури програми. Для кожного нового типу продукту часто потрібно створювати окремий клас-фабрику.
Окремою перевагою цього патерна можна визначити те, що через свою легку масштабованість «Заводський метод» часто може використовуватися в інших патернах. Наприклад, патерн «Адстрактна фабрика» часто реалізується через заводські методи.

3.8	Огляд застосування патерна на конкретному прикладі коду
Розглянемо простий приклад мовою C#. У нас є абстрактний клас Dialog, який містить фабричний метод CreateButton. Конкретні класи WindowsDialog та WebDialog перевизначають цей метод і створюють різні типи кнопок.

 1  // Product
 2  interface IButton
 3  {
 4      void Render();
 5  }
 6  
 7  // Concrete Products
 8  class WindowsButton : IButton
 9  {
10      public void Render() => Console.WriteLine("Windows button");
11  }
12  
13  class WebButton : IButton
14  {
15      public void Render() => Console.WriteLine("Web button");
16  }
17  
18  // Creator
19  abstract class Dialog
20  {
21      public abstract IButton CreateButton();
22  
23      public void RenderWindow()
24      {
25          IButton button = CreateButton();
26          button.Render();
27      }
28  }
29  
30  // Concrete Creators
31  class WindowsDialog : Dialog
32  {
33      public override IButton CreateButton()
34          => new WindowsButton();
35  }
36  
37  class WebDialog : Dialog
38  {
39      public override IButton CreateButton()
40          => new WebButton();
41  }

У цьому прикладі клас Dialog не знає, який саме тип кнопки буде створений. Він працює лише через інтерфейс IButton. Конкретний тип визначається у дочірніх класах. Таким чином ця структура дозволяє нам легко створювати різні форми з кнопками для користувача, не змінюючи загальної структури коду та вже наявні класи і методи.
 
ВИСНОВКИ

У результаті виконання практичного заняття було на конкретному прикладі здобуто знання з основних патернів проєктування коду, описаних у книзі Еріха Ґамми, Річарда Гелма, Ральфа Джонсона та Джона Вліссідеса «Design Patterns: Elements of Reusable Object-Oriented Software». 
Було виконано аналіз патерна «Заводський метод» або «Factory Method» як на теорії, так і на конкретному прикладі коду.
Виконана робота показала, що «Заводський метод» є одним із найважливіших породжувальних патернів проєктування. Його головна ідея полягає у відокремленні логіки створення об’єктів від основної бізнес-логіки програми.
Цей патерн допомагає зробити код більш гнучким, масштабованим та незалежним від конкретних реалізацій. Саме тому він широко використовується у фреймворках, GUI-бібліотеках та великих програмних системах.
Хоча патерн може ускладнювати структуру через збільшення кількості класів, його переваги значно переважають недоліки у великих проєктах. Розуміння «Factory Method» є важливим кроком до побудови якісної об’єктно-орієнтованої архітектури.
